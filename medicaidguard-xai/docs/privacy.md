# Privacy, Responsible AI, and Harm Analysis

This project sits in a domain where a false positive is not a nuisance. An alert
against a home-care caregiver can suspend their income while a review runs; an
alert against an agency can trigger a payment hold that reaches the
beneficiaries receiving care from it. The design decisions below follow from
that, and several of them cost accuracy on purpose.

---

## 1. Data handling

### What this repository contains

Synthetic records only. Every provider, caregiver, patient, claim and EVV event
is generated by `src/medicaidguard/data/generator.py` from a seeded random
number generator. No identifier corresponds to a real person or organisation.
Coordinates are drawn around randomly placed regional centroids in a
mid-latitude bounding box and describe no real address.

### What must never enter this repository

- Real Protected Health Information of any kind.
- Employer data, including claims, authorisations, EVV extracts, member lists
  or provider rosters.
- Real names, addresses, Social Security numbers, Medicaid identifiers, dates of
  birth, or telephone numbers.
- Screenshots of production systems containing member-level data.

`.gitignore` excludes the whole of `data/`, and CI fails the build if a tracked
`.parquet` or `.csv` appears outside `reports/`. These are backstops, not
permission to be careless: a `.gitignore` rule does not remove a file already in
Git history.

### If you adapt this for real data

The repository does not discharge your obligations. At minimum you would need a
business associate agreement where HIPAA applies, minimum-necessary access
controls, encryption at rest and in transit, audit logging of every access to
member-level records, a retention and deletion schedule, and compliance with
your state Medicaid agency's EVV data-use terms. Treat this code as a
methodology reference.

## 2. Privacy threat model

| Threat | Actor | Impact | Mitigation here |
|---|---|---|---|
| Re-identification of a beneficiary from EVV coordinates | Anyone with repository access | Severe — EVV location is effectively a home address plus a presence schedule | Coordinates are synthetic; the API returns distance-derived features rather than raw coordinates in scoring responses |
| PHI leaked through a committed data file | Contributor error | Severe | `data/` gitignored; CI check on tracked data files; documented in CONTRIBUTING |
| PHI leaked through a notebook output cell | Contributor error | Severe | Notebooks in this repository operate on synthetic data only; clear outputs before committing any notebook run against real data |
| Model memorisation of training identifiers | Model design | Moderate | Entity identifiers (`provider_id`, `caregiver_id`, `patient_id`) are excluded from the feature matrix by `schema.GROUP_COLUMNS`; only behavioural aggregates enter |
| Inference of a member's schedule from alert metadata | API consumer | Moderate | No endpoint returns a member's full visit history; provider and caregiver endpoints return aggregates |
| Secrets committed to source | Contributor error | Moderate | No credentials in code; `.env` ignored; `.env.example` documents variables by name only |

## 3. Decision boundaries — what the system will not do

These are enforced in code, not merely stated:

- **No fraud determination.** Outputs are a 0–100 review priority and a
  calibrated probability. No code path emits a boolean "fraudulent".
- **No payment or eligibility decision.** The API exposes no endpoint that
  changes a claim's status, denies a service, or alters an authorisation.
- **No automated action.** Every alert terminates at a human reviewer. The
  `review_status` field defaults to `pending` and is only ever set by a person.
- **No individual is named as fraudulent.** Alerts reference synthetic
  identifiers within a research dataset.

## 4. Human-in-the-loop and appeal

An alert is a *request for someone to look*, and the system is built so that
looking is possible:

- Every alert carries structured rule evidence in plain sentences, not just a
  score. A reviewer can see that billed hours exceeded the authorisation by a
  stated margin, rather than being told a gradient-boosted model returned 0.83.
- Every alert carries the model's calibrated probability and the calibration
  method, so a reviewer knows what a score of 0.4 is supposed to mean.
- Every explanation carries the SHAP interpretation boundary verbatim:
  attributions describe how the model reached its score and are not evidence of
  intent, causation or wrongdoing.
- The rule layer is deliberately retained even though it scores far below the
  learned models, because rule evidence is what survives contact with an appeal.
  A score that cannot be explained to the person it affects is not usable in
  this domain regardless of its AUC.

**Appeal considerations for any real deployment.** The affected party should be
told that an automated system contributed to the review, which factors
contributed, and how to contest the underlying facts. Model attributions are not
a substitute for the underlying records. An alert that cannot be restated as a
factual assertion about the claim should not be actioned.

## 5. Bias and fairness

### What is measured

Experiment 8 reports precision, recall, false positive rate, false negative
rate, PR-AUC and expected calibration error across synthetic demographic
cohorts and service regions. The measurement code is real and reusable.

### What the results mean

**Nothing about real populations.** The cohort labels are randomly assigned in
the generator and carry no relationship to any real group. Observed differences
between cohorts reflect sampling variation and regional differences in the
simulated data. Reporting these numbers as evidence of a fair system would be a
serious misrepresentation.

The experiment's actual purpose is to validate that the fairness measurement
pipeline works, so it can be pointed at real cohorts if this method were ever
evaluated on real data under appropriate governance.

### Bias risks that would be real in deployment

- **Documentation-capacity bias.** Small agencies and independent caregivers
  have less administrative support, so they generate more benign documentation
  anomalies — missing EVV, late submissions, manual entry. A model trained on
  these features will rank them higher without any underlying misconduct.
- **Technology-access bias.** EVV completeness depends on smartphone ownership
  and connectivity. Rural areas and lower-income caregivers will show more
  missing-GPS and telephony-verified visits. The `missing_evv` rule weight
  (0.55, deliberately below the hard rules at 0.85–1.00) reflects that a missing
  record is weak evidence of anything.
- **Language and literacy effects** on data entry quality, which the feature set
  would read as timestamp irregularity.
- **Feedback loops.** If reviewers investigate where the model points and label
  what they find, the next model learns where reviewers went, not where fraud
  is. Any real deployment needs a randomly sampled control stream outside the
  model's ranking to break this.

## 6. Security posture

See `SECURITY.md` for the reporting process and the full threat table. In
summary: no authentication layer is included because there is no real data to
protect; the container drops to an unprivileged user; dependencies are audited
in CI; and the service must not be exposed to an untrusted network with real
data loaded.

## 7. Foreseeable misuse

| Misuse | Why it is foreseeable | Guard |
|---|---|---|
| Presenting a risk score as a finding of fraud | The score looks authoritative and ranges 0–100 | Disclaimer on every scoring response, every dashboard page, and inside the alert narrative itself |
| Quoting the impact simulator as measured savings | Dollar figures are persuasive and travel without their context | Every simulator output field is accompanied by the string "Illustrative scenario-based estimate—not measured real-world savings" |
| Citing synthetic performance as real-world performance | The metrics are strong and the word "synthetic" is easy to drop | Stated in README, research report, dataset discovery report, and the model-info API response |
| Auto-suspending payment on a high score | Operationally tempting at scale | No endpoint exists that could do this; documented as out of scope |
| Using synthetic fairness results to claim the system is unbiased | Superficially it looks like a fairness audit | Stated on the experiment output, in this document, and in the results table note |
